# Build speed audit, 2026-10-15

A read-only audit of what slows the OpenKaava build: Cargo profiles, dependencies, crate layout, the frontend pipeline, CI and tests. Six investigators wrote the findings and six reviewers re-checked each one against the code. Each finding below is confirmed or corrected; refuted findings are left out. Savings are measured where the audit could measure them and say unknown otherwise. No timings were taken.

The findings are ordered by effort. Several overlap; the overlaps are noted in the text.

## 1. Stop building staticlib and cdylib for the desktop app

- **Effort:** trivial. **Affects:** dev-rebuild, release-build, tests. **Review:** confirmed.
- **Evidence:** src-tauri/Cargo.toml:24 crate-type list; lib.rs:104 cfg_attr(mobile); tauri-build-2.6.3 src/lib.rs:475-477 mobile = ios|android only; no tracked gen/android or gen/apple; target/debug/deps/openkaava_orchestrator_lib.lib 1,779,709,704 B and .dll 465,408 B stamped 18:18; target/release/deps/openkaava_orchestrator_lib.lib 203,103,400 B.
- **Change:** In src-tauri/Cargo.toml [lib], set crate-type = ["rlib"]. Restore staticlib and cdylib when a mobile target is actually scaffolded.
- **Saving:** Unknown in seconds. Removes one 1.78 GB .lib write and one DLL link per build that compiles the lib. Archive size is measured; link time is not.
- **Risk:** Mobile builds need the types restored before a mobile target is built. Desktop tauri dev and tauri build should link only the rlib; not run here.

## 2. Drop debuginfo for dependencies and trim it for the app crate

- **Effort:** trivial. **Affects:** dev-rebuild, tests, ci. **Review:** confirmed.
- **Evidence:** No [profile] in any of 8 tracked Cargo.toml; cargo tree gives 373 crates; 199 PDBs = 2.644 GB; openkaava_orchestrator.pdb 345,616,384 B; lib test-harness PDBs 265,310,208 and 260,026,368 B; .rustc_info.json split-debuginfo packed.
- **Change:** In the root Cargo.toml (a [workspace] root with members src-tauri, crates/*, examples/echo-tool), add [profile.dev] debug = "line-tables-only" and [profile.dev.package."*"] debug = false. If the wildcard also catches the app crate, name it explicitly with its own override. The test profile inherits dev, so cargo test follows.
- **Saving:** Unknown in seconds. The measured ceiling is the 2.644 GB of PDBs, of which dependency PDBs are a large share. Codegen and link effect not measured.
- **Risk:** Debugger steps into dependencies lose symbols; line-tables-only drops locals in app code. Keep debug = 2 for workspace crates if locals are needed for debugging.

## 3. Delete target/debug/incremental locally; no CI change

- **Effort:** trivial. **Affects:** dev-rebuild. **Review:** corrected.
- **Evidence:** target/debug/incremental = 11,565,093,998 B, 7,301 files; session dirs 12 (lib) and 10 (bin); verify.yml:102-104 uses Swatinem/rust-cache@v2; rust-cache README:166-168 and src/restore.ts:30 set CARGO_INCREMENTAL=0; scripts/kaava-ui.mjs:36-37 honours CARGO_TARGET_DIR.
- **Change:** When no cargo process is using the target directory (check CARGO_TARGET_DIR first), delete target/debug/incremental. Leave [profile.dev] incremental on; the next build recreates it. Do not add CARGO_INCREMENTAL to verify.yml.
- **Saving:** 11.565 GB of disk, measured. Rebuild time unknown; the first incremental build after deletion is a cold codegen of the app crate.
- **Risk:** Deleting under a build running in the same shared target dir would make that build fail or re-run. Check for running cargo processes first.
- **Reviewer note:** Local half confirmed: target/debug/incremental is 11,565,093,998 B (11.565 GB) across 7,301 files, with 12 openkaava_orchestrator_lib and 10 openkaava_orchestrator session dirs. target/debug/deps is 7.821 GB and target/release is 3.982 GB. CI half refuted: the Swatinem/rust-cache README (lines 166-168) says the action sets CARGO_INCREMENTAL=0 automatically, and its src/restore.ts:30 exports CARGO_INCREMENTAL=0 (fetched with gh api). verify.yml:102-104 therefore already builds without incremental, so the proposed env line is a no-op and Swatinem pruning is moot. Local deletion has a sharing caveat: scripts/kaava-ui.mjs:36-37 honours CARGO_TARGET_DIR, and parallel agents share target dirs per memory, so no cargo process may be using the directory.

## 8. Pin Rust via rust-toolchain.toml and make the workflow install that pin

- **Effort:** trivial. **Affects:** ci, dev-rebuild. **Review:** corrected.
- **Evidence:** verify.yml:91 installs 'stable' explicitly; PR log line 251 shows the stable update that moved the cache key (main log lines 273-274 show Rust 1.99.1 in the key hash).
- **Change:** Add a root rust-toolchain.toml with channel 1.99.1 and components clippy, rustfmt. Change verify.yml:91 to install the file's toolchain (for example rustup show, or rustup toolchain install with no name) rather than stable, and verify on the runner that it reads the file. Bump the pin in a deliberate PR.
- **Saving:** Unknown. A rustc change invalidates the environment hash and forces a cold dependency rebuild on that run only; that cold build is not measured here.
- **Risk:** Local toolchains must match the pin and download 1.99.1. The pin stops picking up stable fixes until someone bumps it. Wrong workflow edit causes two toolchain downloads per run.
- **Reviewer note:** Confirmed log line 251: 'stable updated - rustc 1.99.1 (from 1.99.0)'. Confirmed main log lines 273-274: cache key environment hash includes Rust Versions 1.99.1, key v0-rust-verify-Windows_NT-x64-15d0a0c1-b3e24605. Confirmed no rust-toolchain file and no .cargo dir. Correction: the install line is verify.yml:91 (run block starts line 90), and it names 'stable' explicitly, so it installs the stable channel and does not read a rust-toolchain.toml. Without a change to that line, each run would install stable and then rustup would also download the pinned version for cargo, i.e. two toolchains. The workflow must install the pinned toolchain (for example rustup show, or rustup toolchain install with no name, which reads the file); behaviour on the runner unverified here.
